# Plan — Selección espacial y preparación de cobro

**Goal:** seleccionar un espacio real por intervalo y descriptor humano, y habilitar cobro solo después de configurar policy conscientemente en Console.
**Architecture:** modular hexagonal existente; proyección pública independiente, mapper humano puro compartido y motor existente readonly. Bootstrap conecta módulos; ningún contexto importa otro.
**TechStack:** Angular 22 / Signals / Vitest, MapEnginePort + Konva instalado, Spring Boot 4.1.1 / Java 25 / Jackson 3, PostgreSQL 17 / Flyway, Playwright; Node 24 / pnpm 11.9.0.
**Spec:** [spec.md](./spec.md), aprobada por usuario el 2026-10-27 mediante «Aprobar especificación».
**Estado:** confirmado por el usuario el 2026-10-27 mediante «Confirmar y ejecutar»; implementación autorizada dentro de los scopes descritos.

## GlobalConstraints

- Lanes B/M/C/F/Q con scopes exclusivos; C y F en sesiones distintas. Sin worktrees, cambios de rama, commits, push, reset, cleanup ni reversión de cambios ajenos en workspace sucio.
- El nuevo alcance autoriza backend/contrato/migraciones/libs: el veto backend anterior no rige esta ampliación. No cambiar datos del negocio ni elegir moneda/importe/plazo de Pollos. Sin defaults de dinero/capacidad, policy automática o fallback MOCK. Sin instalaciones/dependencias/Figma/panzoom/motion nuevos.
- Contrato primero: B edita OpenAPI → `pnpm api:lint` → `pnpm api:gen` y estabiliza interfaces. Único codegen por B; nadie edita/versiona `generated/`. El script actual genera TS, no afirmar generación Java no existente.
- Metadata opcional y vigente, no snapshot. Diario legacy sigue solo disponibles; nueva proyección usa AVAILABLE/RESERVED/UNAVAILABLE, no ocupación live. Reserva continúa rechazando estado operativo no AVAILABLE incluso para el futuro.
- Reutilizar pagos V20–V27 y su sesión/URL/QR por intento, idempotencia, STOMP, recibos y métodos tradicionales. Nueva migración solo metadata, sin backfill ni reparación local; actualizar DBML.

## 1. Contratos concretos y handoffs

### B: API pública y metadata

1. Conservar `GET /api/v1/public/tenants/{tenantSlug}/establishments/{establishmentSlug}/availability`, operationId **`findPublicAvailability`**, modelos `PublicAvailability/PublicAvailabilityElement` id/type y exclusión diaria de no disponibles.
2. Añadir **GET `/api/v1/public/tenants/{tenantSlug}/establishments/{establishmentSlug}/availability/map`**, operationId **`findPublicAvailabilityMap`**, tag `public-availability` → servicio generado `PublicAvailabilityService.findPublicAvailabilityMap`. Parámetros `date` obligatorio, `startTime/endTime` opcionales HH:mm, ambos o ninguno; errores 400/404 `Problem`. Sin horas: día completo local, sin permitir continuar al nuevo booking sin intervalo. Respuesta propia **`PublicAvailabilityMap`**:
   - `establishmentId`, `establishmentName`, `tenantSlug`, `establishmentSlug`, `timezone`, `date`, `startTime/endTime` nullable, `startsAt/endsAt` ISO instante, `mode` DAY/INTERVAL y `floors: PublicMapFloor[]`.
   - **`PublicMapFloor`**: `id,name,level,canvasWidth,canvasHeight,sectors:PublicMapSector[]`.
   - **`PublicMapSector`**: `id,name,width,height,x,y,rotation,elements:PublicMapElement[]`. width/height intrínsecos; x/y/rotation son placement persistido en piso; elemento x/y relativo al sector, sin recalcularlo al mover el sector.
   - **`PublicMapElement`**: `id,type,label` nullable, `name` derivado, `capacity` nullable, `x,y,width,height,rotation`, `selectable` boolean, `availability` AVAILABLE/RESERVED/UNAVAILABLE. `selectable` expresa elegibilidad actual del resultado, no hold. Sin attrs, estado operativo, reservas ajenas ni PII. DECOR puede dibujarse como contexto UNAVAILABLE; no cambia elegibilidad de otros tipos: reutilizar regla backend vigente, no TYPE_DEFAULTS de Console.
3. Ampliar **`SpaceElement`** de OpenAPI (respuesta staff), **`SpaceElementCreateRequest`** y **`SpaceElementUpdateRequest`** con `label/capacity` opcionales nullable; respuesta los incluye y añade **`name` derivado**, no columna name. Mantener operationIds `createSpaceElement`, `updateSpaceElement`, `getSpaceElement`, `listSpaceElementsBySector`, `deleteSpaceElement` y geometría actual.
4. **`CheckoutSpace`** mantiene `id,name,floor,sector,state` y añade `type,label,capacity,x,y`. Nuevas propiedades de respuestas previas se declaran opcionales en OpenAPI para compatibilidad de clientes/fixtures; backend sí las emite (label/capacity pueden ser null). Nuevos DTO map/readiness sí tienen su allowlist requerida. `name` deja de ser UUID, y las vistas de reserva propia/puertos de bootstrap transportan metadata/posición vigente. La UI muestra ubicación con x/y cuando label falta o se repite. No añadir displayName paralelo: **label es único dato persistido; name es salida canónica derivada**. Export público de api-client ya reexporta generated: no requiere escribir fuentes manuales compartidas.

No IDs bancarios, cuentas, secretos ni tokens.
